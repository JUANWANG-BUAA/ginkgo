# 学生工作台与信息降噪设计

日期：2026-10-28。本文是产品设计，不表示功能已经实现或真实验收。未完成事项只在 [MIRROR-TODO.md](MIRROR-TODO.md) 维护；已有能力以 [MIRROR-IMPLEMENTATION.md](MIRROR-IMPLEMENTATION.md) 和源码为准。协议事实以 [API.md](API.md) 为准，候选公开来源及历史证据见 [DATA-SOURCES.md](DATA-SOURCES.md)。

## 1. 问题与目标

学生要从不同系统寻找课程、截止事项、资讯和办事入口；它们的时效、受众和操作风险不同。目标是让用户先看到与自己有关且需要行动的事项，能判断信息是否可靠，再按任务找到其他服务。不要把所有学校入口平铺到首页，也不要声称门户搜索结果等于全校服务的完整清单。

用户指出课程、作业、个人待办和截止提醒已完成：它们是现有基线，不应作为第一阶段新增集成。按用户确定的顺序，先验收当前改动，再完善 **服务目录与本地搜索**，随后逐步接入就业活动、讲座、教务通知和办事指南；工作台保留已有近期事项。既有 P0 认证、安全和可复现回归仍先于扩展；Windows 保持共享代码可编译，Apple 冻结。保留现有五个移动标签，不以本方案批准更换导航或新增学校写操作。

## 2. 当前基线与差距

| 能力 | 工作树现状 | 本设计要解决的缺口 |
| --- | --- | --- |
| 工作台 | 今日课程、学校作业、个人待办分别读取；课程与作业局部刷新，作业展示最近三项；已有下一节课焦点和常用服务 | 作为已实现基线保留；现有可靠性及验收缺口继续按原待办处理 |
| 考试、签到 | 考试随课表读取；签到是独立业务，存在手动提交 | 是否可低成本、安全地复用已有结果需先核查；第一阶段不为首页新增自动读取、签到或考试提醒承诺 |
| 本机提醒 | 作业、签到及课程/待办已有本地提醒相关实现和设置；Android 权限、重启等验收仍在待办 | 以既有能力为基础梳理截止信息、去重与开关，不能将本地调度说成准时送达 |
| 服务与资讯 | 已有分组服务目录、常用入口、校园通知、公开查书、校车时刻表；当前校园通知页面为北航新闻网最新五条；本人借阅、校园卡工作树已接入但真实验收未完成 | 新增学生教务来源和按来源浏览；目录搜索后续复用现有入口，不把入口当已验证接口 |

上述事实指工作树而非发布范围；借阅认证和校园卡真实金额等验收限制继续按现有记录维护。历史 [IA 方案](NEXT-STAGE-IA-2026-10-23.md) 可作参考，其第五栏迁移只是候选，不是本方案的决定。

## 3. 既有工作台约束

本节保留工作台的设计约束，以下线框和排序是可选优化，不构成本轮新增集成目标，也不意味着现有能力缺失。具体实现只在发现可复现问题时按原待办处理。

工作台按用户任务组织：

```text
工作台
  正在 / 下一节课             已有课程焦点，进入课表
  近期考试                   仅在有明确考试时显示，无卡片占位
  学校作业 / 本机待办        保留原分区，不重复聚合时间线
  状态与局部重试             与相关来源相邻，不以整页失败覆盖其他内容
  常用服务 / 全部服务        沿用原有 iOS 分组列表和二级搜索页
```

2026-10-28 后续复核移除了近期时间线，避免重复展示课程、作业、待办和签到。考试只在有未早于学校今天的记录时显示；加载、失败和成功为空均不占位。服务目录保留原有 iOS 分组列表与交互，不改变既有视觉语言。

“近期事项”是各来源的**呈现投影**，不合并学校和本地状态、不创建新的学校待办。学校作业显示课程、截止时间和来源，点开原作业；本机待办显示本机标记、用户设定的时间，点开待办。已有关联学校作业的历史本机记录沿用现有去重规则；不得恢复作业详情“加入个人待办”入口。保留原有完整作业与待办页面的可达性。

建议首屏最多展示 3 条有明确时间的近期事项，按时间从近到远排列；余项通过“查看全部”进入来源页面或明确的汇总视图。无时间的待办及状态未知的作业单独说明并可进入原页面，不编造时间，不因缺少时间而称为已完成。已截止的未完成作业明确标记“已截止”，不能当作未来截止；不以个人待办完成推断学校提交。先覆盖已有来源，再根据实际使用反馈决定时间窗口和其他来源；不凭推测展示“全部事项已完成”。

时间使用学校时区和既有业务规则：精确截止可显示日期、时间和剩余时间；仅有日期时只展示日期，不虚构具体时刻或倒计时。相同时间按稳定来源和 ID 顺序展示；未知或无法解析的时间归入待确认，避免排序跳动。规则归 Rust domain，Dart 负责纯呈现；先复用或迁移现有截止规则，避免两套判断。

### 数据状态

| 情况 | 界面行为 |
| --- | --- |
| 首次加载 | 各来源独立显示加载，不阻塞已完成的区域 |
| 确认成功为空 | 仅对成功的来源说没有相关事项；其他来源未确认时不显示全局空态 |
| 刷新失败、有旧数据 | 保留旧内容、来源和原成功时间，提示可能过期并提供局部重试；失败不延长 TTL |
| 失败、无旧数据 | 明确该来源不可用和可重试，不转成空结果 |
| 多来源部分成功或数据不完整 | 展示成功部分并明确未更新/不完整来源；现有作业契约不能表达的部分成功先补契约，不能虚构完整性 |
| 换账号或服务代次 | 清除旧页面状态，丢弃迟到响应；不能混入另一账号的事项 |

## 4. 截止提醒

提醒是用户可控制的辅助功能，不代表学校已处理，也不能保证操作系统准时送达。沿用已有开关、授权和排程入口；既有提醒的设备验收按原待办推进，不新增全局后台抓取、个人数据预取或自动写学校状态。用户关闭或撤销系统权限时提供可理解状态和进入系统设置的路径；不使用虚假成功提示。

以稳定来源与事项标识区分提醒，变更/完成/删除或账号切换时取消或更新对应本地排程，重复刷新不产生重复提醒；不得取消其他账号或其他类型的排程。无可靠截止时间、已截止、已提交或状态不明时不推断可以发送新的截止提醒；旧快照不得冒充最新状态。涉及具体既有触发规则的修改，先对照现有设置和测试，避免悄然改变用户选择。设备重启、强停、省电策略与通知权限仍需分别验收，不把 widget 或模拟器结果等同真机送达。

## 5. 学生公开教务通知

当前“校园通知”只列新闻网最新五条，不能覆盖分散在教务部和研究生院网站的学生通知。在服务目录和就业活动之后，建议在既有资讯入口增加 **教务部学生专区通知** 和 **研究生院通知** 两个公开只读来源，保留新闻网来源，并让用户按来源浏览；先逐源核实页面、字段、分页与访问条件，再决定能否接入。历史观察见 [数据源清单](DATA-SOURCES.md)，不视为本次实时验证或已实现协议。

用户能看到标题、发布机构、发布日期、简短来源说明和官方原文入口；能选择本科相关或研究生相关来源，也能切回全部。首页只提供到资讯的入口，不把所有通知提升为紧急事项，不默认发送通知或提醒。发布日期不是办理截止日；正文没有可靠、经验证的结构化截止日期时不做倒计时或个人待办。详情先以官网原文为准，避免擅自解析复杂附件、名单或把文章当个人通知。

每个来源独立加载和刷新，保留其最近成功数据与时间；来源失败时明确提示并允许单独重试，成功空与解析结构变化分开表达。按发布时间排序，时间缺失标为未知；仅以可验证的来源内稳定标识去重，不按相似标题跨来源合并。用户手动打开资讯时读取，缓存与请求频率按实际协议和现有架构确定，不后台批量抓取。新的学校协议先补 [API.md](API.md) 的证据与修订对照；真实公开页复核不等于 Android 设备验收。

完成标准：两来源各完成一条 domain → upstream → core → bridge → Flutter 的只读纵向链路，复用或扩展已有通知模型，展示来源筛选、原文跳转与各来源状态；提供正常、空、结构漂移、单源失败和缓存回退的合成回归，并单独记录公开源、设备和网络验收。若某来源无法验证，则保留明确的官网入口与未接入状态，不伪装成成功。

## 6. 服务目录与其他公开信息

**服务目录**：沿用原有 iOS 分组列表，在现有静态登记和目录上逐步统一稳定 ID、名称、学生常用别名、领域、目的地和“应用内 / 官方网站”标记；不重复维护页面工厂。二级搜索页仅查询本机服务元数据，提示“不搜索个人记录”；搜索不请求学校系统，返回时保留查询和位置。官方入口需核实目标地址，明确离开应用，不传 token、不承诺免登录。先覆盖现有可达服务，再补经过核实的高价值入口；不能因门户搜索无结果断言学校没有相关服务。

**其他公开信息**：后续评估就业活动及讲座，按用户选择的来源、主题和日期筛选。只逐源接入经过取证的公开信息，不默认抓取全站、不自动建立个人画像。食堂、电话、门诊等静态指南先核实更新机制与维护责任，再决定是否原生展示。具体来源优先级和协议证据需复核，旧资料中的优先级不是排期承诺。

**个人只读扩展**：借阅到期、网费或其他个人状态只有在认证、字段、权限及隐私边界验证后才讨论进入工作台；本人借阅当前真实认证未打通，校园卡余额工作树已接入但真实验收未完成。余额保持按需查询、默认遮挡、不进入首页预取。资金写操作不接入；现有签到/预约等写能力继续遵守用户触发确认、单次提交和回查，不因本设计新增或自动化写操作。

## 7. 分层、验收与成功标准

页面消费 `application` 契约，使用现有 `RefreshSection` 等状态管理；学校协议和解析只在 upstream，稳定日期与截止规则在 domain，core 编排，bridge 输出类型化结果，native/demo 共享契约。仅为展示调整时不增加桥接 API；确需跨层变更时按现有生成流程更新 FRB 和接口索引。多来源投影不引入全局个人数据索引，不把 Cookie、token 或学校原始响应带入页面。

既有工作台调整如涉及以下情形，继续遵守相应回归要求；本轮新增资讯的完成标准见第 5 节：

1. 合成数据下课程、学校作业、本机待办在不同完成顺序、同一截止、无时间、已截止、未知状态及跨北京时间午夜时正确展示；详情返回保持原导航行为。
2. 一源失败、旧快照、成功空、部分结果、强制刷新重叠、切账号和迟到响应均不产生错误的“全部完成”或跨账号信息；保留来源和原成功时间。
3. 提醒开关、权限拒绝、重复刷新、事项变更/删除、账号切换均可回归，且不触发学校写入；涉及通知服务和持久化时按仓库隐私与人工审查规则执行。
4. Android 窄屏、大字号、深浅色、系统返回、TalkBack 和至少 48dp 触控目标得到相应层级验证；共享代码保持 Windows 可编译。执行 `bash scripts/check-mirror.sh` 和 `git diff --check`；真实账号、物理设备和系统后台行为分别记录，未做不勾选。

产品效果先以可复现任务观察：从资讯入口找到教务或研究生通知、确认来源并打开原文所需步骤，以及用户能否识别未更新来源；使用合成场景和自愿反馈，不预设提速数字、不采集个人事项内容。后续来源优先级是可调整的设计假设。
