# 研究生缓存与网络等待复核（2026-10-21）

## 已确认问题

`SessionService.load_graduate_part` 在查询五分钟快照前等待 `graduate_request_gate`。因此，即使学籍快照有效，另一个正在进行的报告请求仍可阻止学籍返回；反方向亦然。这是缓存路径的队头阻塞，不依赖上游响应内容。

macOS `GraduateAcademicViewModel.load` 先发布已有缓存再执行刷新；镜像应使已有快照不依赖另一个模块网络完成。两端持久化与TTL仍不同，本次没有把进程缓存改成磁盘缓存。

## 修复及证据

先检查已登录身份和有效快照；只有缓存未命中或强制刷新进入GSMIS网络锁。取得锁后重新校验身份和缓存，前一个请求已经填充快照时不重复请求。保留GSMIS认证激活的串行保护，强制刷新失败保留同一分区旧快照。

两个确定性测试直接持有异步锁并单次poll，不用真实网络或计时猜测：

- 有效缓存读取必须在锁仍被持有时完成；强制刷新必须等待。释放锁后模拟网络失败，仍返回旧快照与失败状态。
- 缓存未命中请求等待锁期间，前一请求填入缓存；取得锁后复用该结果，HTTP请求数为0。

首个测试在原实现失败；修复后两个测试均通过。相关研究生过滤测试14项通过（含这两项）；Clippy all-targets/all-features通过。此修复不改变FRB签名或Dart模型。

## 验收边界

该证据确认应用层缓存阻塞，不证明用户手机“切页才刷新”的全部原因。模拟器当前正常登录页，尚未取得本轮真实会话耗时。后续按普通Wi-Fi、自动路线记录iclass、图书馆、研究生首次加载/缓存返回/强制刷新的耗时、状态与条数；不保存真实响应正文、课表或截图。真实写请求只由用户手动确认执行。

## 手动学校接口耗时检查

设置新增“学校接口耗时”，需要正常学校登录；离线演示只显示登录提示。仅用户点击后依次读取场馆、当前预约、iclass当天课程、研究生学籍与执行报告，完成一项立即发布一项。普通读取允许缓存，可重复比较；强制刷新显式忽略缓存。显示耗时、条数、可用的缓存标记、旧结果与错误码，不保留响应正文或异常字符串，不写文件/上传报告。

顺序检查降低额外并发负担，测得的是应用层完整调用耗时（含必要认证与排队），不是单个HTTP连接耗时，也不模拟用户同时打开多个页面。研究生现有DTO不提供缓存标记，本页不凭耗时猜缓存命中。页面关闭后不继续发下一项，已发只读调用仍受现有bridge预算；不能把检查页当真实业务页面即时刷新的替代验收。
