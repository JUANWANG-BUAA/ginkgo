## 理论设计框架（当前理解）

### 前后端边界定义

**前端不应该知道：**
- HTTP 状态码（应该是业务错误类型）
- 重试逻辑细节（应该是"操作成功/失败"）
- 后端的中间步骤（应该是完整的业务响应）
- 数据库 ID 的格式（应该是强类型 DTO）
- 时间戳的本地计算（应该是后端给的快照时刻）

**后端应该保证：**
- 每个 FRB 命令是完整的业务操作（不需要多个命令组合）
- 错误被分类为"业务级错误"（NoCredential, InvalidInput, Conflict）而非"网络错误"
- DTO 只包含用户界面需要的字段
- 状态和判定逻辑在后端完成（不推给前端 if-else）
- 时间戳格式统一（都用 UTC ms）

### UI 设计框架

**iOS 设计的六条规则（文件：docs/UI-DESIGN.md）：**

1. **系统控件优先** — 不要自定义刷新、选择、空态
2. **一级导航固定五个** — 今天/课表/作业/图书馆/更多
3. **一屏一问** — 每页回答一个问题，不混杂功能
4. **每页一条汇总** — 列表前必须有摘要行（SummaryStrip/Line）
5. **状态三件套** — 状态 = 文案 + 颜色 + 图标
6. **口径一行** — 来源和时间只占一行 footer

**设计 token 体系已建立：**
- `GinkgoColors` — 深浅色适配的语义颜色
- `GinkgoTypography` — 字号、行高、字重
- `GinkgoSpacing` — 间距规范（8, 12, 16, 20, 24, 32...）
- `GinkgoRadii` — 圆角（4, 8, 12, 16...）
