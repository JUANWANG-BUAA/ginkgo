# BUAA Assistant - 人 + AI 合作开发指南

> 本文档定义本项目开发过程中人类开发者与 AI 编码代理（如 ZCode、Claude Code、Copilot 等）的分工、流程与红线。它不是通用指南——每一条都针对本项目的具体形态：单人开发者 + AI 代理，做一个直连北航上游系统的原生 macOS 应用。

## 0. 为什么需要这份指南

本项目 2026-10-13 的文档审查暴露了纯 AI 产出文档的典型失败模式，也是本指南的立论基础：

1. **AI 会编造不存在的接口**（旧版 API.md 中 `courseTable.do`、`grade.do`、`opac/api.php` 均无出处）；
2. **AI 会混淆接口归属**（把 UBAA 中转服务器的 `/api/v1/*` 路由当成北航上游直连接口）；
3. **AI 会生成似是而非的代码**（用 iOS 的 `tabBars`/`swipeLeft` 写 macOS 测试、调用不存在的 `waitForNonExistence` API）；
4. **AI 会污染隐私**（示例中反复写入真实学号与姓名）。

结论：AI 的产出**产能高但不可免检**。人 + AI 的正确关系是「AI 出草案、人掌事实和决策、流程强制校验」。

## 1. 角色分工

### 1.1 人类负责（不可下放）

| 职责 | 说明 |
|------|------|
| **产品决策** | 做什么功能、什么体验、里程碑取舍（如「借阅查询降级为探索项」这类决定） |
| **事实裁决** | 上游接口的真实行为：AI 给出的任何协议断言，最终以人的抓包/真机验证为准 |
| **逆向取证** | 用本人账号在浏览器操作上游系统、导出 HAR（AI 不得接触真实凭据） |
| **真机验收** | 真实账号端到端走通的功能才能标记「已验收」（Mock 通过 ≠ 可用） |
| **安全审查** | 凭据存储、网络策略、隐私裁剪，每次涉及时人工过目 |
| **上游写操作** | 预约、取消、选课等会改变上游状态的动作，只能由人手动触发 |

### 1.2 AI 负责（主力产能）

| 职责 | 说明 |
|------|------|
| **代码生成** | 按 API.md 已验证章节实现 Service/Parser/ViewModel/View 及配套测试 |
| **重构与迁移** | 从 UBAA（BBAA 仓库）Kotlin 实现对照移植为 Swift |
| **测试编写** | 单元/集成/UI 测试、黄金文件用例、快照更新 |
| **文档同步** | 代码变更后更新 API.md 对应节并在修订对照表登记 |
| **协议比对** | 人提供 HAR 后，AI 做脱敏、字段比对、结构归纳 |
| **调试分析** | 给定日志/截图/复现步骤，AI 定位候选原因并给出验证步骤 |

### 1.3 边界共识

- AI 产出的一切**默认是草案**，进入主干前必须过 §4 的审查清单；
- 人不必写代码。优先做到「让 AI 解释到能用自己的话复述」；确实无法理解的改动，退而求其次必须通过运行验收（Cmd+R 跑通 + 行为符合预期）且测试全绿——两条路径至少走一条；
- 反过来，人抓的 HAR、真机截图、验收记录是 AI 拿不到的信息，**不要省略这一步**。

### 1.4 不熟悉 Swift 时的协作模式（当前实际模式）

> 本节假设：人类开发者不熟 Swift/SwiftUI，AI 承担全部编码。原 §1.3 的「读代码」要求按本节降级。

**人的不可下放职责不变**（产品决策、抓包取证、真机验收、隐私安全把关——这些都不需要 Swift 知识），语法正确性交给四道兜底：

1. **运行验证代替阅读验证**：每个模块的完成定义（DoD）=「Xcode Cmd+R 跑起来，人工点一遍符合预期 + `xcodebuild test` 全绿」。§4 审查清单中「事实层/安全层」人工执行，「代码层」由测试与运行替代。
2. **合并前讲解**：AI 用中文讲清「做了什么、为什么、哪里最容易出错」；追问后仍讲不清的改动拆小重做。讲解过程即学习过程。
3. **LEARNING.md 机制**：每次合并后，AI 将本次用到的 Swift 概念（optional、actor、@MainActor 等）以「概念 + 一句话解释 + 本项目真实例子」追加到 `docs/LEARNING.md`。人只复习此文件，不要求系统学课程。
4. **Git 小步提交**：一个模块一个 commit；不确定的改动先在分支跑两天再合入。

**最小生存知识清单**（人花半天到一天）：`let/var`、optional（`?`/`!`/`guard let`）、`struct` 与 `class` 区别、`async/await`、SwiftUI「界面是状态的函数」这一思想。其余概念遇到时问 AI。

**预期管理**：ARCHITECTURE.md §8 的周期按熟练 Swift 开发者估算；本模式下按 2-3 倍预期，Phase 1 首周目标缩小为「菜单栏 App 可运行 + 登录页可见」。

## 2. 三条核心工作流

### 2.1 功能开发流（Feature Loop)

```
人：明确功能与验收标准（一行话说清"做到什么算完成"）
 ↓
人：确认 API.md 对应章节是 ✅ 已验证
   ├─ 是 → 继续
   └─ 否（⚠️/缺失）→ 先走 2.2 逆向取证流，补齐文档再回来
 ↓
AI：按文档实现（Service + Parser + ViewModel + View + 测试，一次任务一个模块）
 ↓
人：Code Review（§4 清单）→ 跑测试 → 真机验收
 ↓
AI：同步文档（API.md 若有勘误/补充，登记修订对照表）
 ↓
人：合并
```

节奏建议：一次让 AI 做一个**可独立验收的模块**（如「GSMIS 课表解析器 + 测试」），不要一次生成整个 App。

### 2.2 逆向取证流（Reverse-Engineering Loop）——本项目最高价值的人机协作

参照 UBAA 的审计方法（`BBAA/docs/_audit/2026-09-17-ihome-api.md` 是范本）：

```
人：用本人账号在浏览器正常使用目标功能，DevTools 导出 HAR
 ↓
AI：解析 HAR——请求清单、参数、响应结构、鉴权头；自动脱敏（学号/姓名/票据替换为合成值）
 ↓
AI：输出取证报告草稿，每条断言标注证据条目（E1、E2…对应 HAR entry 序号）
 ↓
人：抽查关键断言（鉴权头、写操作语义、成功码），纠正 AI 的过度推断
 ↓
人：对写操作做一次真实往返验证（如关注→回查→取消→回查），AI 根据结果定稿语义
 ↓
AI：将结论写入 API.md 对应章节（✅ 标记 + 证据引用），原 HAR 不入库
```

铁律：**HAR 原件与含真实凭据的任何文件不进仓库**；取证报告里只保留结构，不保留内容。

### 2.3 缺陷修复流（Debug Loop）

```
人：提供复现步骤 + 现象（日志/截图/上游响应片段，脱敏后）
 ↓
AI：列出候选原因（按概率排序），每个给出"如何证实/证伪"的检查步骤
 ↓
人：执行检查，回传结果
 ↓
AI：定位根因，给出修复 + 回归测试
 ↓
人：验证修复 + 确认回归测试真的能抓住这个 bug（先看它在旧代码上变红）
```

禁止 AI 直接「猜一个修法就提交」。没有复现路径的 bug 不修。

## 3. AI 使用红线（本项目专用，违反即打回）

1. **证据强制**：AI 产出的任何上游接口断言（URL、参数、字段、成功码、鉴权格式）必须附带出处——BBAA 仓库的文件:行号、或本项目 `_audit` 取证报告的条目号。给不出出处的，写成 `⚠️ 待验证` 而不是陈述句。
2. **不编造 API**：Swift/XCTest/SwiftData 的 API 拿不准时，标注「需查证」，由人验证或要求 AI 先给出官方文档出处。上游接口同理。
3. **成功码不许抽象**：各系统成功判定不一致（`"0"`/`"1"`/Int 0/`code∈{0,1}`，见 API.md 附录 C），禁止 AI「顺手统一」成常量——这是上游事实，不是代码坏味道。
4. **隐私脱敏**：任何文件（代码、测试、文档、快照、fixture）出现真实学号/姓名/手机号/Cookie/票据即打回。统一用 `sy2501001`、`李文`、`张三` 等合成值。
5. **写操作不自动重试**：预约/选课类 POST 的失败重试逻辑只能由人设计评审后加入；AI 生成的通用「重试拦截器」默认不得应用于写操作（上游多为切换语义，重发会反向操作）。
6. **安全四件套人工过目**：Keychain 读写、TLS 信任配置、日志输出、网络权限（App Sandbox entitlements）——这四类 diff 无论多小都要人审。

## 4. 人工审查清单（每次合并前）

### 4.1 事实层（最重要）

- [ ] 本次涉及的接口调用与 API.md ✅ 章节逐项一致（URL、方法、参数名、参数值、请求头、成功码）
- [ ] 没有新增「无出处」的接口断言
- [ ] 字段解析对照过 DTO/快照（尤其 `xf/kccj` 类型漂移、`snake/camel` 双写变体）

### 4.2 安全层

- [ ] 无凭据/会话落入日志、UserDefaults、明文文件
- [ ] Keychain 用法：`kSecAttrAccessibleWhenUnlockedThisDeviceOnly`
- [ ] TLS 无静默放宽（若为图书馆证书链问题放宽，必须限定域名+评审记录）
- [ ] 隐私裁剪：展示层不输出上游响应中的他人个人信息

### 4.3 代码层

- [ ] 测试先红后绿（针对 bug 修复）；新功能有测试
- [ ] 错误路径有 UI 呈现，不是静默吞掉；**每个 catch 至少留一条 OSLog 日志**再决定吞或抛（教训依据：DEEP-REVIEW §15——UBAA 客户端零日志基础设施 + 5 处空 catch）
- [ ] 「预期失败」（如未登录、格式不支持）与「程序缺陷」的文案区分开，前者给出可行动提示
- [ ] UI 符合 ARCHITECTURE.md §10 的 HIG 约束抽查（语义色、Reduce Motion、无障碍标签）

### 4.4 文档层

- [ ] API.md 与实现同步；如有出入，以实现时发现的真实行为为准**改文档**并登记修订对照表

## 5. 仓库与文档约定

1. **`docs/` 是唯一事实源**。各文档的分工：
   - `ROADMAP.md`：开发说明书（任务分解、验收标准、常见坑）
   - `API.md`：上游协议（证据分级 ✅/⚠️）
   - `ARCHITECTURE.md`：技术决策与结构
   - `TESTING.md`：测试策略
   - `BACKLOG.md`：候选功能储备（A-D 级分级与接入规则）
   - `ACCEPTANCE.md`：验收记录（每 Step 验收后追加，规则见 ROADMAP 附录 A）
   - `DEEP-ARCHITECTURE-REVIEW.md`：UBAA 参考实现的透视（只读参考，不随本项目代码更新）
   - `COLLABORATION.md`（本文）：协作规则
2. **修订可追溯**：改 `API.md` 必须在 §0.0 修订对照表登记（改了什么、证据是什么）。被否决的旧说法保留更正注记而非直接消失——这正是旧版文档出错后难以追溯的教训。
3. **取证产物**：放 `docs/_audit/`，命名 `YYYY-MM-DD-<主题>.md`；HAR 原件、含 PII 的导出一律不入库。
4. **分支与提交**：`main` 保持可用；每个功能/修复开分支 `feat/<模块>` / `fix/<问题>`；提交信息中文一句话说清动机（参照 BBAA 仓库风格）。例外：Step 0 骨架初始化与纯文档勘误可直接提交 `main`。
5. **CI（Phase 1 建立）**：`xcodebuild test` + 快照回归 + 上游巡检（TESTING.md §9/§10）。

### 5.6 工具链：Xcode（人）+ 终端 AI 代理（AI）

**结论：人用 Xcode，AI 在终端干活；VSCode 非必需。** Xcode 反正必须安装（macOS App 的 SDK、签名公证、UI 测试运行器都在其中，编辑器无法替代）。

| 角色 | 工具 | 用途 |
|------|------|------|
| 人 | Xcode | 一次性建工程、Cmd+R 运行、SwiftUI 预览（仅 Xcode 有）、控制台看日志、点界面做验收 |
| AI | 终端（ZCode 等） | 编辑 .swift 文件、跑 `xcodebuild -scheme BUAA-Assistant build/test`、git 操作 |

关键工程配置（Phase 1 建立时执行）：

1. 用 **Xcode 16+** 创建工程，保持默认的**文件系统同步文件夹**（synchronized groups）模式——AI 在磁盘新增 .swift 文件后 Xcode 自动纳入编译；
2. **红线：AI 不得手改 `.xcodeproj` 工程文件**（pbxproj 格式脆弱、diff 不可审）。需要改工程配置（新 target、entitlements、capability）时，由 AI 给出步骤、人在 Xcode 界面操作；
3. App Sandbox、Keychain 共享等 entitlements 变更属 §3 红线 6 的安全审查范围，人工执行；
4. UI 测试（XCUITest）由 AI 编写，用 `xcodebuild test -only-testing:BUAA_AssistantUITests` 在 CI 或本机跑。

## 6. 分阶段落地（对齐 ARCHITECTURE.md §8 里程碑）

| 阶段 | 人的关键动作 | AI 的关键动作 | 出口标准 |
|------|--------------|----------------|----------|
| Phase 1 基础框架 | 定 Xcode 工程与签名；验收登录（含验证码/密码过期分支） | 脚手架、CAS 登录全链路实现 + Mock 测试 | 真实账号可登录、登出；会话过期可恢复 |
| Phase 2 课表+成绩 | 双门户真机验收；抓当前学期真实响应做脱敏快照 | GSMIS/BYXT 解析器 + 周视图 + buaascore 查询 + GPA | 本科+研究生各验收一个真实账号；快照回归进 CI |
| Phase 3 图书馆+增强 | 图书馆 TLS 证书链实测；预约做一次真实往返后取消 | 座位模块（含 AES-CBC）、通知、快捷键 | 预约→列表→取消闭环人工验收通过 |
| Phase 4 优化完善 | 性能/无障碍抽查 | 性能修复、错误路径补全、文档终稿 | TESTING.md §11 清单全绿 |

借阅查询（探索项）：完成 API.md §6 验证清单前，不出现在任何里程碑里。

## 7. 协作提示词模板

### 7.1 新功能实现

```
实现 <模块名>。
依据：docs/API.md §<N>（✅ 已验证），架构遵循 docs/ARCHITECTURE.md §<M>。
范围：只做 <Service/Parser/ViewModel/View> 这一层 + 对应测试。
要求：
- 每个上游调用旁注释 API.md 节号；
- 不确定的 Swift API 标注「需查证」而不是猜；
- 示例数据用合成值（sy2501001/李文）；
- 完成后列出你做了哪些与文档不一致的临场决定（应当为零，若有说明文档有问题）。
```

### 7.2 逆向分析（配合人提供的 HAR）

```
分析附件 HAR（目标功能：<...>），产出取证报告草稿：
- 请求清单表（方法/路径/参数/证据条目号）；
- 每条断言标注 [E<n>] 或 [源码佐证] 或 [待验证]；
- 自动脱敏：学号/姓名/票据替换为合成值后输出；
- 明确列出「样本无法确认」的清单（分页、错误分支、过期行为等）。
```

### 7.3 调试

```
问题：<现象一句话>
复现：<步骤>
已观察：<脱敏后的日志/响应>
请：按概率列候选根因，每条给出证实/证伪的检查步骤。先诊断，不要给修复代码。
```

### 7.4 文档同步（合并前）

```
对照本次 diff，检查 docs/API.md 是否需要更新：
- 实现中发现的文档偏差（以真实行为为准修正文档）；
- 在 §0.0 修订对照表登记改动与证据；
- 不确定的行为标注 ⚠️ 待验证，不要写成事实。
```

### 7.5 合并前讲解（不熟 Swift 时必用）

```
用中文给我讲解本次改动，按此结构：
1. 一句话：这次改了什么、为什么；
2. 数据流：用户点击 X → 依次经过哪些文件/函数 → 界面如何变化（用文件名+函数名）；
3. 本次用到的 Swift 概念（附一句话解释，追加到 docs/LEARNING.md）；
4. 最容易出错的 3 个点，以及出错时界面会是什么表现；
5. 如何在 Xcode 里手动验证（点哪里、期望看到什么）。
我不熟悉 Swift，避免术语堆砌；每个术语第一次出现时解释。
```

## 8. 风险与边界提醒

- **合规**：本项目是个人使用的校园服务客户端，协议逆向仅限本人账号、正常使用范围内的观察；不做批量请求、不做绕过风控、不协助他人绕过认证。
- **上游变化是常态**：任何「昨天还能用」的功能坏掉，先跑巡检和快照回归定位变化点，再走 2.2 流程更新文档。
- **AI 的知识截止**：AI 对北航上游系统的全部「知识」都应该来自本仓库文档与取证报告，而不是它的训练记忆——凡是它凭记忆说出的上游细节，一律要求降级为待验证。
