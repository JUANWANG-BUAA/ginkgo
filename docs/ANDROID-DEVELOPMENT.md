# Android 主开发与功能体验设定

> 生效：2026-10-22。用户已确认以 Android 为当前主开发平台，并同意以“今天 2.0 + 作业转待办 + 相关 UI 打磨”为首批方向。本文是开发设定与目标，不表示功能已实现、已发布或已验收。

## 1. 产品目标与优先级

**让 Ginkgo 从校园查询工具集合，变成每天打开就知道下一步做什么的个人校园工作台。**

- 当前主线：Android 的新功能、日常使用体验与 UI；Flutter + Rust 继续作为实现栈。
- 功能与体验主导，稳定性托底；不以清完全部技术债为新功能前置。
- 每轮交付一个用户可感知的闭环，同时补齐涉及的异步、缓存、账号隔离与失败态回归。
- Windows 保持共享代码兼容，不为本轮额外扩展桌面功能；macOS/iOS 保留原生 SwiftUI，本轮默认不改 Apple 产品代码。
- Android 优先不等于允许破坏其他平台。公共 Rust/Flutter 契约变化须同步消费者、生成绑定与相关测试。

## 2. 首批范围

| 工作包 | 本轮目标 | 不扩大的边界 |
| --- | --- | --- |
| 今天 2.0 | 突出下一节课、近期截止作业、个人待办；按时间与状态组织，事项可定位到相关页面/详情 | 不新增启动全模块拉取；预约摘要在已有可复用状态且不增加首屏阻塞时接入，否则后续做 |
| 作业转待办 | 用户主动添加，预填标题、来源、截止时间（存在时），可编辑并回到来源；同账号同来源同作业防重复 | 本地完成不等于学校提交；不自动修改学校作业状态，不新增上传/作答/提交 |
| UI 打磨 | 工作台、作业详情、待办形成连续流程；统一层级、间距、状态和主要操作 | 不一口气重画全部页面，不为换皮引入全局状态框架或完整设计系统重写 |
| 相关可靠性 | 分区独立加载、保留旧数据、账号切换隔离；验证提醒初始化与前后台竞态 | 不新增无界轮询，不承诺后台常驻或通知准时到达 |

以下是首版建议默认，可在实现评审时细调，并非新增用户授权：

- 下一节课优先展示时间与地点；截止事项按明确的时间升序，已完成收起；无截止时间的待办单独展示，不伪造日期。
- 作业转待办保留来源系统与稳定作业标识；来源缺可靠标识时明确降级，不仅凭标题合并不同作业。
- 重复添加时定位已有待办，不覆盖用户编辑；学校数据刷新不自动改写用户待办，也不因作业消失删除待办。
- 截止时间缺失时允许不设截止，或要求用户主动选择；不擅自变为今天到期。现有模型不支持时先扩领域契约与迁移回归。
- 日期计算遵循学校时区，按账号保存个人数据与偏好；来源标识不作为可跨账号读取数据的凭证。
- 有可验证来源定位时打开详情；只有站点入口时明确标注，不假装支持作业深链。

## 3. Android UI 与交互原则

- **一眼可行动**：首屏回答“下一节是什么、最近什么要交、现在能做什么”，不把多个模块目录重新堆成卡片墙。
- **延续而非推倒**：沿用现有银杏主题、语义色与简洁分组；iOS 页面是既有信息层级参考，不要求逐像素复制，也不强制全量 Material 化。
- **Android 行为优先**：正确处理系统返回/返回手势、键盘与安全区域、通知权限；详情返回恢复合理位置和筛选，不突然退出应用。
- **手机优先**：窄屏单列、主要操作易触达，控件目标以至少 48dp 为起始验收值；大字号下允许换行与重排，不压缩文字维持漂亮网格。
- **信息而非装饰**：统一字级、间距、行高、圆角和状态色，复用已有主题/组件；不用大面积渐变、装饰玻璃或持续动画代替层级。
- **可信状态**：加载中、确认空、失败、旧缓存、部分成功分别呈现；显示最后成功同步时间，不把未知显示为零。
- **稳定刷新**：有数据时不替换整屏，不因局部失败抹掉其他区域；旧响应不覆盖新账号或新查询，避免交互中自动重排和跳顶。
- **无障碍**：TalkBack 能读出标题、来源、时间、状态与动作；不只靠颜色；遵循系统减少动态效果设置。
- **分区复用**：课程/作业已有渐进加载和提醒复用机制，先复用再扩展，不把已有能力包装为新建成果。

## 4. 后续候选，不默认纳入首批

1. 未来七天聚合视图，明确已查询周次/日期和来源覆盖范围。
2. 常用入口置顶、低频区域折叠及按账号记忆筛选；模块拖拽排序后置。
3. 用户主动导出课表日历文件；系统日历写权限和双向同步另行评审。
4. 校车、讲座/宣讲会、校园办事指南；先复核 [数据源](DATA-SOURCES.md) 与协议证据，再决定接入。
5. 余额/借阅等登录只读能力需取证；充值、自动签到及未经验证的上游提交不属于本轮。

## 5. 工程与安全边界

- 遵守 [工程边界](MIRROR-ARCHITECTURE.md)：domain 定义模型/端口，core 承担应用规则，upstream 管学校协议/会话/缓存，runtime 组装，bridge 只映射命令与 DTO。
- Flutter 经功能 gateway 消费类型化结果；页面不解析学校响应、不读取 token、不直接调用生成函数。展示排序可在呈现层，学校日期和稳定业务规则留在 Rust。
- 作业转待办涉及持久化模型时必须兼容旧数据，并验证失败不覆盖、损坏保护和账号隔离；不将个人待办当查询缓存清除。
- 仅桥接 API 变化时运行 FRB 生成脚本；生成文件不手改，Rust 库与 Dart 绑定配套构建。
- 学校接口事实以 [API](API.md) 为准，新增断言附证据；不统一各系统成功码，不臆造端点。
- 学校写操作仍需用户明确触发、确认、单次提交与回查；结果不明禁止自动重发。点击首页事项不等于授权提交。
- 不改弱 TLS，不提交真实凭据、票据或个人数据；认证、保险库、日志及权限变更遵守 [协作规范](COLLABORATION.md) 的人工审查。

## 6. 执行与验收

建议顺序：**合成数据的今天 2.0 页面样板 → 作业转待办闭环与数据兼容 → gateway/真实数据接入 → Android 设备体验验收**。贯穿修复影响首批体验的正确性问题，不先全量模块化。

每个工作包完成必须满足：

- 规则回归：时间边界/跨午夜、未知截止、重复添加、完成状态独立、账号切换与旧数据迁移。
- 页面回归：加载/空/部分失败/缓存状态；点击定位、返回、重复点击；迟到响应与前后台切换。
- Android 设备检查：窄屏、大字号、深浅色、TalkBack、系统返回和权限拒绝；真实结果与合成演示分别记录。
- Rust/Flutter 基线：仓库根执行 `bash scripts/check-mirror.sh`；该脚本包含依赖解析，不宣称纯离线。若桥接变化，另做生成差异检查。
- 产物检查：在 flutter/ 执行 `flutter build apk --debug --target-platform android-arm64 --target lib/main.dart`；不能把 integration_test 生成的 APK 当正常启动包。
- 真实网络/学校写往返不由 widget 测试或 APK 构建代替；真实写入只在用户逐次人工授权下验收。
- 记录改动、自动化结果、设备观察及尚未覆盖的边界；不在设定文档提前写“已完成”。

后续任务默认先说明这轮用户可感知的变化，再给实现、测试和限制。新增系统、扩大写操作或大幅改变导航/视觉方向时先确认；已约定范围内按小步、可回滚方式推进。

用户版更新说明（GitHub Release 正文与应用内更新内容）统一保持简短：每版3–5条，每条一句，只说“这次改进了什么、用户用起来有什么变化”。不堆测试数量、技术名词、源码/签名/打包过程或完整验收清单；这些放维护记录。涉及数据丢失、不兼容升级或重要安全限制时另用一句明确提醒，详细内容链接展开。没有实质变化不凑条数，不写尚未完成的功能；历史已发布正文不自动改写。
