# 认证协议冻结 (Beta 9+)

**生效日期**：2026-11-03
**原因**：Beta 3-8 中认证改动导致账号风控。为防止再次发生，冻结认证协议至少 3 个月。

## 禁止改动

以下内容**绝对禁止修改**，任何改动需要用户明确授权并通过真实账号验收：

### 协议层（网络请求）
- ❌ CAS 登录提交逻辑 (`auth/session.rs`, `gateway.rs`)
- ❌ 验证码处理和提交 (`session_protocol.rs`)
- ❌ WebVPN 回退条件和重试策略
- ❌ Cookie 管理和发送逻辑
- ❌ 密码冷却和重试策略
- ❌ 首屏触发的任何认证请求

### 前端表现
- ❌ 登录页流程
- ❌ 验证码输入界面
- ❌ 路线切换触发时机
- ❌ 任何自动化认证路径

## 允许改动

以下改动**可以进行**，无需真实账号验收：

### 允许
- ✅ UI 文案和翻译
- ✅ 错误提示文本
- ✅ 本地缓存策略（不改网络）
- ✅ 日志和诊断信息
- ✅ 测试覆盖（合成数据）

### 条件允许
- ✅ Bug 修复（必须：离线回归通过 + 代码审查）
- ✅ 性能优化（不改协议 + 合成测试）

## 改动审查流程

任何可能影响认证的改动必须：

1. **离线验证**（必须）
   - 通过 `bash scripts/check-mirror.sh` 全量
   - 补齐合成测试用例（直连失败、WebVPN 回退、验证码过期等）
   - Dart 侧 Flutter test 全量通过

2. **代码审查**（必须）
   - 至少 2 人评审
   - 确认无额外网络请求
   - 确认无自动密码提交

3. **真实账号验证**（仅维护者）
   - 仅在用户明确授权情况下
   - 必须在风控恢复后（24h 冷却期）
   - 验证场景：正常登录、WebVPN 切换、验证码失败恢复
   - 记录完整验收证据

4. **发布前确认**
   - 用户明确同意该改动
   - 提供完整改动说明和风险评估
   - 准备回滚方案

## 历史教训

### Beta 4 - 首屏隐式认证
```
改动：新增首屏签到读取
问题：直连失败 → WebVPN 重试 → 学校验证码
现象：用户打开首页看到登录提示（不应该）
后果：用户困惑 + 风控触发
```

**防止方法**：任何认证请求必须是用户主动操作的结果

### Beta 5-7 - 验证码白名单
```
改动：验证码处理只接受 type: "local"
问题：真实账号验证码 type: "image" 被拒绝
现象：用户无输入通路
后果：用户反复尝试 → 风控激活
```

**防止方法**：所有验证码类型必须被接受和处理

### Beta 4-7 - 密码重复提交
```
改动：9 个模块各自 60s 冷却
问题：模块 A 失败 60s 后重试，同时模块 B/C/D... 也各自重试
现象：1 分钟内 9 次密码提交
后果：学校风控激活 → 账号冻结 3-24 小时
```

**防止方法**：密码冷却必须是全局的，不是模块级的
