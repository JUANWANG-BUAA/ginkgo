# Android 核心链路可靠性收口设计

日期：2026-10-27  
状态：设计建议，未实施  
范围：Android（Flutter + Rust）；Windows 只保持共享代码可编译；macOS / iOS 继续冻结  
关联清单：[MIRROR-TODO](../../MIRROR-TODO.md)

## 1. 结论

下一轮不应继续优先扩展功能，也不应进行全量状态管理或五层架构重写。应立即做一次**核心链路可靠性收口**，顺序如下：

1. **P0：消除退登阻塞并补齐本地失败语义。** 退登先完成本地身份与凭据清理，远端注销不得长期占住全局会话锁；传输失败保留可测试的类别，写操作仍不得自动重放。
2. **P0：建立隐私安全的诊断与故障注入闭环。** 当前异常在 Flutter 公共刷新路径中被折叠成 `localService`，首读高延迟又缺少足够阶段证据。先让故障“可定位、可复现”，再改并发或恢复策略。
3. **P0：用当前公开版本完成一次受控真实只读复验。** 区分 Alpha.4 的 HTTP SSO 跳转修复、后续版本和当前 Alpha.9 的实际结果；不连续提交密码，不把旧证据当作当前可用。
4. **P1：补作业课程归属的部分成功契约。** 主列表成功、学生/助教课程归属失败时，不能静默显示成完整结果。
5. **P1：完成物理 Android 设备验收。** TalkBack、预测返回、大字号、深浅色、长列表帧率和厂商后台行为不能继续只由模拟器与 widget 测试代替。

真实签到、图书馆、CGYY 和作业提交验收仍是发布可信度的必要边界，但它们需要用户逐次人工操作，不属于可自动执行的开发批次，也不能因本轮自动化通过而标记完成。

## 2. 判断依据

### 2.1 已经做得好的部分

- Rust 分层、学校协议隔离、页面不直接读取生成命令等约束已有架构门禁，不需要推倒重来。
- 读命令已有 45 秒上界，登录/恢复和主要写命令已有 90 秒上界；强制刷新补跑、await 后账号复检、写状态四态映射等早期问题已经修复并有回归。
- 查询失败保留旧快照及原成功时间；学校写入采用用户确认、单次提交和回查，未知结果禁止自动重发。
- Android Keystore、显式退出、账号代次、更新产物校验等边界已具备实际实现与测试。

因此，重复实施 2026-10-24 评审中的第一批修复，或一次性重写所有页面，都会浪费当前已经有效的安全网。

| 优先级 | 缺口 | 当前证据 | 用户或维护影响 |

### 2.3 对旧审计结论的修正

设计实施时不得机械照抄旧审计：

- `login` / `restore` 和主要写命令的 90 秒上界已经存在，不能再次当作新任务；本次只补退登这一处实际遗漏。
- `docs/update-gate.json` 已在当前工作树中，Android release workflow 也已存在，不能再按“文件未进 main / 无发布 workflow”处理。`minBuild` 仍为 5，但在确认新版本可下载前不得贸然提高。
- `reqwest` 的 HTTP 5xx 仍通过 `HttpResponse.status` 交给上层，并非都被 `TransportError` 吞掉。当前被压平的是传输构造、连接/发送、body 读取、任务 join 和响应大小类失败。
- 当前 Android 作业主链是 SPOC，不应照搬 Swift 历史“多来源作业”模型。这里要修的是**同一作业流程中的课程归属补充读取失败**。
- Dart 的 25 组强连通分量、`ReadOnlyResponse.payload`、token 采纳率和 domain 规则归位仍有价值，但均不应排在上述可靠性问题之前。

## 3. 方案比较

### 方案 A：继续功能扩展

优点是能快速增加可见能力；缺点是最新认证、失败定位、部分成功和物理设备证据继续缺口，新增能力会复用同一批不可靠路径。**不采用。**

### 方案 B：全量架构与状态管理重构

统一 core 快照编排、删除全部 JSON 袋、迁移所有业务规则并统一页面控制器，长期有收益；但跨域 diff 大，难以将故障与行为变化隔离，也会延迟真实问题修复。**不作为本轮方案。**

### 方案 C：小步可靠性收口（推荐）

保持五层架构、gateway、缓存和写状态机不变，只修改退登时序、内部错误分类、诊断上下文、作业补充读取状态和对应测试。每个切片均可独立回滚，并能以合成故障验证。**采用。**

## 4. P0 设计：退登与会话边界

### 4.1 目标时序

退登调整为“本地安全状态优先，远端注销有界且尽力而为”：

1. bridge 获取 `SESSION_ACCESS` 写锁，防止新读写进入旧身份。
2. upstream 取当前账号，递增身份代次，清除认证状态、Cookie、业务 token 和查询快照。
3. 删除保存的账号凭据；删除失败保留现有有限重试与显式错误记录，不因远端网络而推迟这一步。
4. 使用独立的 `bounded_logout`（10 秒）等待远端 logout。超时或失败只记录安全诊断，不把本地退登回滚，也不自动重发。
5. 再次清理身份与快照，释放锁，向 Flutter 返回本地已退出状态。

远端注销属于认证会话操作，不应套用学校业务写入的 `uncertain` 状态；页面只需区分“本机已退出”和“远端注销未确认”。`SessionResponse` 增加可空 `remote_logout_confirmed`：仅退登命令返回 `true` 或 `false`，其他命令为 `null`；Dart 对应 `bool? remoteLogoutConfirmed`。远端未确认时非阻塞提示“已在本机退出；学校远端注销未确认”，显式退出标记继续阻止下次启动自动恢复。

### 4.2 约束

- 不在等待远端 logout 后才删除凭据；远端阶段总等待预算固定为 10 秒，不叠加自动重试。
- 不新增密码提交，不因为远端 logout 失败而重新登录。
- 不改变 CAS 白名单、Secure Cookie、TLS 校验和现有显式退出语义。
- 凭据枚举失败不得被解释为“没有保存账号”；沿用各平台保险库已有的 fail-closed 行为。
- 不在诊断中记录账号、Cookie、service 参数或远端响应正文。

### 4.3 验收

- 远端 logout 永久 pending 时，本地身份、快照和保存凭据仍及时清理，bridge 在既定预算内返回。
- 远端 logout 返回 401、500 或超时，下一次启动都不会自动恢复已显式退出的账号。
- logout 期间账号切换、路线切换和迟到的业务读取不能把旧身份写回。
- 正常远端 logout 仍只发送一次请求。

## 5. P0 设计：错误语义与隐私安全诊断

### 5.1 Rust 传输错误

在 `ginkgo_upstream` 内部把 `TransportError` 拆成有限类别：

- `Connect`：DNS、TCP 或连接建立失败；
- `Tls`：证书与 TLS 握手失败，能可靠识别时才使用；
- `Timeout`：连接或读取超时；
- `ResponseTooLarge`：声明长度或实际累计字节超过上限；
- `Cancelled`：传输任务被取消或 join 失败，无法进一步分类时也归入此类；
- `Unavailable`：其余无法可靠分类的传输失败，作为保守兜底。

不得把 `reqwest` 原始错误字符串放入领域错误或日志。无法可靠区分的错误宁可使用 `Unavailable`，不得为了提高分类率猜测 TLS 或超时原因。

这些类型首先服务 upstream 测试与恢复决策；现有 `ErrorCode` 和 Flutter `FailureCode` 本轮不扩张。学校业务拒绝、认证失效、协议漂移仍由 adapters/codecs 按原规则分类，HTTP 状态不得统一塞进 `TransportError`。

### 5.2 Dart 诊断事件

将 `DiagnosticLog` 从“只有错误码和时间”扩展为有上下文的内存事件：

| 字段 | 允许内容 |
| --- | --- |
| `id` | 本地时间戳加单调序号，用于用户反馈 |
| `feature` | 固定枚举，如 `session`、`checkin`、`bykc`、`graduate`、`homework` |
| `operation` | 固定枚举，如 `login`、`restore`、`signOut`、`load`、`refresh` |
| `outcome` | `success`、`stale`、`failure`、`localFailure`、`remoteLogoutUnconfirmed` |
| `failure` | 现有 `FailureCode?` |
| `elapsedMs` | 本地实测耗时，不伪造阶段进度 |
| `hasExistingData` | 是否保留了旧内容 |
| `at` | 事件发生时间 |

事件只保留内存中最近 50 条，沿用现有容量边界；不自动上传、不写普通偏好、不保存学校载荷。用户主动复制诊断时，也只导出上述白名单字段。

`failureMessage` 改为纯文案映射，不再在调用文案函数时产生日志副作用。日志应在命令完成或异常捕获处记录一次，避免 build 重入和重复事件。`RefreshSection` 接收固定的诊断上下文，在未知异常时记录 `localFailure + localService`，同时保留功能、操作、耗时和旧值信息，而不是丢掉全部上下文。

### 5.3 首读性能测量

先覆盖 `session`、`checkin`、`bykc`、`graduate` 和 `homework`，记录整条命令及已有恢复阶段的实际耗时。iClass 继续复用 `CheckInLoadProgress`，不另造虚构百分比。博雅和研究生只有在证据显示需要用户反馈时，才增加类似的真实阶段进度。

第一轮不得仅凭总耗时做以下改动：增加全模块并发、缩短认证冷却、提高自动恢复次数或新增轮询。若测量证明瓶颈在串行独立请求，再为对应模块单独设计有界并发；每次自动认证仍必须合并，且每轮读取最多恢复一次。

### 5.4 故障注入矩阵

使用现有 `HttpTransport` 合成实现和 Flutter gateway fake，不访问真实账号：

| 场景 | 必须保持的行为 |
| --- | --- |
| 连接失败、TLS 失败、读取超时、响应超限 | 返回既定失败类别；原始错误文本不跨层 |
| 首读失败且无缓存 | 显示失败与重试，不伪造空结果 |
| 刷新失败且有缓存 | 保留旧值和原成功时间，显示旧数据提示 |
| 成功后空结果 | 覆盖旧数据，不当作失败 |
| 认证失效 | 最多一次合并恢复；失败进入冷却，不形成请求风暴 |
| 超时取消 | HTTP 任务被中止，后续刷新不积累孤儿请求 |
| 飞行中切账号 | 旧结果被丢弃，不写新账号缓存 |
| 写请求超时或断网 | 结果为 `uncertain`，只允许回查，禁止自动重发 |

## 6. P1 设计：作业课程归属的部分成功

### 6.1 领域契约

在 `HomeworkData` 增加独立的补充读取状态，不把主列表和补充信息揉成一个 `failure`：

```text
HomeworkData
  termCode / termName / items
  roleEnrichment
    studentCourses: EnrichmentState
    assistantCourses: EnrichmentState

EnrichmentState = complete | unavailable(AppError)
```

`AppError` 留在 domain/upstream 边界，bridge 再映射为 Flutter 的 `FailureCode`，不让领域层依赖 FFI 类型。主作业列表成功即保留主数据及主列表 `fetched_at`；任一课程归属读取失败时，对应状态为 `unavailable`。两项都成功才是 `complete`。缓存同时保存该状态，TTL 内命中也不能把旧的 partial 伪装成 complete；强制刷新可重试补充读取。

不使用字符串 source id，不让 Dart 解析学校端点。bridge 将上述领域枚举映射为 DTO，FRB 绑定通过生成脚本更新；demo 同步提供完整、部分失败和主列表失败三种合成场景。

### 6.2 页面语义

- `complete`：保持现有页面，不增加多余提示。
- 任一 `unavailable`：显示“作业列表已更新，但课程归属未完整更新”，提供仅针对该读取流程的刷新入口。
- 课程归属未知的条目继续按现有保守规则保留，不自动推断为学生或助教，不伪造零条待办。
- 主列表失败且有旧缓存：继续显示“正在显示上次结果”，不与补充读取 partial 混为一谈。
- 主列表失败且无缓存：显示错误态，不显示“本学期无作业”。
- 本轮不改变个人待完成统计算法；先在独立 widget 测试中明确未知归属的现有口径，避免借提示修复夹带统计规则变化。

### 6.3 验收

至少覆盖：两项归属都成功、仅学生课程失败、仅助教课程失败、两项都失败、主列表失败、旧缓存 partial、强制刷新恢复 complete、账号切换迟到结果、未知课程 ID。每种场景同时断言数据、提示、缓存时间和课程角色，不只断言页面没有崩溃。

## 7. 真实验收门禁

### 7.1 当前认证只读复验

由账号所有者明确授权后，在 Alpha.9 正常入口包上执行：

1. 记录版本、路线、日期和失败阶段，不记录密码、Cookie、完整 service 或响应正文。
2. 单次登录，不连续重试；核对 CAS → UC 链是否仍出现 HTTP SSO 跳转及当前客户端是否正确升级。
3. 成功后只读检查工作台、课表、SPOC 作业，以及目标账号有权限的一个业务模块。
4. 冷启动与显式退出各一次，验证恢复和凭据删除符合选择。
5. 若出现 `InvalidCredentials`、验证码或学校策略拒绝，立即停止自动尝试，保留分类，不推断封号或绕过风控。

结果单独写入带日期的验收记录；成功空结果、非空数据、账号类型和路线不可互相外推。

### 7.2 学校写操作

签到、图书馆、CGYY 和文件作业继续逐次由用户本人触发和确认。每次记录提交前状态、单次请求、结果分类和回查；结果不明禁止重发。代理不得自动执行这些真实写入。本轮任何自动化结果都不得勾销 `MIRROR-TODO` 中的人工验收项。

### 7.3 物理 Android

至少在一台真实 ARM64 设备覆盖：预测返回、TalkBack 主流程、320dp 等效窄屏与大字号、深浅色、长列表滚动、通知权限拒绝/恢复、强停与重启。厂商省电和后台行为按设备分别记录，不写“Android 已全部通过”。

## 8. 实施切片与完成标准

以下只是设计的工作分解，执行状态仍只维护在 `MIRROR-TODO`，不另建第二份待办：

1. **退登切片**：调整 upstream 时序与 bridge 有界等待，补 pending/失败/迟到响应测试。
2. **诊断切片**：拆传输错误、扩展白名单诊断、纯化 `failureMessage`，完成合成故障矩阵和首读耗时证据。
3. **作业 partial 切片**：扩领域与 DTO、生成 FRB、接 native/demo 和页面提示，补缓存与 widget 回归。
4. **验收切片**：在当前正常入口包执行授权只读与物理设备检查；真实写入单独安排。

前三个代码切片各自必须：

- 先添加能复现原问题的回归，再修改实现；
- 通过 `bash scripts/check-mirror.sh`；桥接 API 变化时同步 FRB 生成差异；
- 构建正常 `lib/main.dart` Android ARM64 包，不以 integration test 包代替；
- 执行 `git diff --check`，同步受影响的架构、接口和实施文档；
- 明确自动化、模拟器、物理设备、真实只读和真实写入各自证据，不把“工作树完成”写成“已发布/已真实验收”。

## 9. 非目标

- 不新增校园功能、写能力、自动签到或自动打卡。
- 不新增自建中转服务器，不放宽 TLS、Cookie 或认证白名单。
- 不做全量 `ReadOnlyResponse` DTO 改造、token 全面替换、Dart 循环依赖清理或 core 快照模板大重构。
- 不引入新的全局状态框架、通用日志框架或自动上传诊断。
- 不恢复作业详情“加入个人待办”入口。
- 不处理冻结的 Apple 功能，也不要求 Windows 新功能验收。
- 不提高 `minBuild`，除非目标新版本已公开可下载且用户存在可自救的更新路径。

## 10. 后续触发条件
